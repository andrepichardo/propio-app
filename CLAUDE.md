# Propio — agent notes

SaaS for independent landlords. Next.js 16 App Router (Turbopack) · React 19.2 · TS strict · Prisma 7/PostgreSQL (Supabase) · Auth.js v5 · next-intl v4 · Tailwind 4 + shadcn-style UI in `src/shared/components/ui`.

## Commands

- **Yarn, not npm** (`yarn.lock` is the lockfile): `yarn dev` · `yarn build` · `yarn typecheck` · `yarn lint` · `yarn test`
- **Two TypeScripts on purpose** (see Gotchas): `yarn typecheck` runs **TS 7** (the Go compiler, ~0.3s); `yarn typecheck:ts6` runs TS 6.0.3, which is what ESLint, Next and the IDE actually see. `yarn lint` is the ESLint CLI (`next lint` was removed in Next 16 and `next build` no longer lints).
- DB: `yarn db:push` (dev), `db:migrate`, `db:seed` (demo@propio.app / Demo1234!)
- Copy `.env.example` → `.env`; minimum `DATABASE_URL` + `AUTH_SECRET`.

Do NOT add `reply_to` without asking. If it is ever wanted: the receipt replies to the OWNER, the three account emails to `info@`, and the privacy clause that promises the sending address accepts no replies has to change with it.

## Architecture rules (follow these when adding code)

- **Feature-based**: `src/features/<name>/{validators,repositories,services,actions,components}`. Routes in `src/app` stay thin and delegate.
- **Multi-tenancy is the law**: every domain table has `ownerId`. Repositories put `ownerId` in EVERY where clause. Get it via `requireOwnerId()` (`src/shared/lib/auth/session.ts`). Cross-entity writes (e.g. contract→property) must verify ownership first.
- **Server actions**: build with `createOwnerAction(schema, handler)` from `src/shared/lib/action.ts`. It handles auth + Zod + error→`ActionResult<T>` mapping. Client forms pattern-match `result.success` and use `applyFieldErrors` (`src/shared/hooks/use-server-action.ts`).
- **Errors**: throw typed errors from `src/shared/lib/errors.ts` in services; never leak raw errors to the client.
- **Optional fields must be CLEARABLE**: build them with `optionalText(max)` / `clearEmpty` from `src/shared/lib/validation.ts`, never with a bare `.transform((v) => (v === '' ? undefined : v))`. Prisma reads `undefined` as "leave this column alone", so mapping an emptied input to it makes clearing impossible — the save reports success and the old value comes back (this shipped, affecting every optional text field in all six features). The three states: field omitted → `undefined` (untouched), field emptied → `null` (cleared), otherwise the value. Services must not collapse that `null` back with `|| undefined`; the exception is upload-managed URLs (`avatarUrl`, `coverImageUrl`, `invoiceUrl`, `proofUrl`), which forms never submit and which keep `|| undefined` on purpose.
- **Soft deletes**: set `deletedAt`; never hard-delete domain rows. Reads filter `deletedAt: null`. **`paymentService.remove` is the one deliberate exception** — it hard-deletes, cascading the `Receipt` row (`onDelete: Cascade`) and removing both blobs (receipt PDF, proof) from storage. A voided payment must leave no receipt behind, so this is intentional; see the receipt-numbering note for what it implies.
- **Money**: Prisma `Decimal(12,2)`. Format with helpers in `src/shared/lib/format.ts`; never do float math on display values.
- **Storage**: only through `getStorage()` (`src/shared/lib/storage`) — never import the Supabase driver directly. When re-uploading to a FIXED key (avatar, signature, receipt PDF), store the URL with `?v=${Date.now()}` to bust browser/CDN caches.
- **Lists**: filters/pagination live in the URL query string, validated with a Zod `*FiltersSchema` before hitting services.
- **Every route section** gets `loading.tsx` (skeleton) + `error.tsx` (re-export `@/shared/components/route-error`). Skeletons must MIRROR the real view (same cards/grid/field density, mobile-first, no overflow) — detail/form/list pages each have their own; form-page skeletons compose primitives from `shared/components/form-skeleton.tsx`. **A page that also has child routes must live in a route group**, together with its `loading.tsx`. A `loading.tsx` is a Suspense boundary for its segment AND everything below it, so an index skeleton left beside its children flashes for one frame before the child's own skeleton takes over (visible on the first navigation, then hidden by the router cache until a reload). Applies at BOTH levels:
  - index → children: `(list)` in `payments`, `tenants`, `contracts`, `properties`; plus `app/app/(overview)` (dashboard) and `app/app/settings/(preferences)`.
  - detail → edit: `[id]/(detail)` in `tenants`, `contracts`, `properties`.
  `error.tsx` stays at the SEGMENT root on purpose — error boundaries should cover the children. Route groups don't change any URL.
  Audit rule: no directory may hold `page.tsx` + `loading.tsx` while also containing child route directories. The one deliberate exception is `src/app` itself, whose `loading.tsx` is a plain full-screen spinner meant as the global fallback, not a page-shaped skeleton.
- **Comment sparingly.** A comment earns its place when the code cannot state the reason itself: a non-obvious constraint, a library bug being worked around, a decision whose alternative looks more sensible than it is. Routine changes — a spacing tweak, a renamed prop, a reordered import — get none. Match the density of the file you are editing; do not narrate diffs.
- No `any`. `import 'server-only'` in server-only modules. Barrel exports per feature are optional; avoid importing server code into client bundles.

## i18n (EN + Latin-American ES — everything user-visible is translated)

- next-intl v4, **cookie-based** (`NEXT_LOCALE`, no URL prefix). Infra in `src/i18n/`; catalogs in `src/messages/{en,es}.json` — every new string goes in BOTH.
- Client → `useTranslations('ns')`; async server → `getTranslations('ns')`; tab titles via `generateMetadata` + `meta` namespace.
- **Zod messages are i18n KEYS** from the `validation` namespace (e.g. `.min(1, 'firstNameRequired')`); `FormMessage` translates them with a `t.has()` fallback. Enum labels: constants export `*_VALUES`, render with `t(\`ns.${value}\`)`.
- `src/i18n/request.ts` honours an explicit `getTranslations({ locale })` BEFORE falling back to the cookie — required for `after()` callbacks and PDFs/emails rendered in the OWNER's language. Normalize `prefs.locale` with **`toLocale()`** (`i18n/config.ts`) first; the column is free text and may hold a BCP-47 tag.
- **Never pass a stored locale straight to `Intl` — use `numberLocale()`** (`i18n/config.ts`). `setLocale` writes bare `'es'`, which `Intl` reads as SPAIN: `40.000,00`, while every market this app serves writes `40,000.00`. It shipped that way in the receipt email and the whole statement PDF while the receipt PDF alone mapped to `es-DO`, so one tenant got the same amount formatted two ways in one message. Unit-tested in `i18n/__tests__/config.test.ts`.
- **Activity feed is data-driven i18n**: `logActivity` takes `messageKey` + `params` stored in `Activity.metadata` as `{key, params}`; the dashboard translates at render via the `activity` namespace and falls back to the English `summary` for legacy rows. Notifications (`title`/`body`) still store English text — same pattern applies if ever requested.
- Language switcher (topbar) uses **SVG flags** (`src/shared/components/language/`) — never emoji flags (Windows renders them as letters). It's the only place a USER changes the UI language (`setLocale` sets the cookie + mirrors `User.locale`); there is no language field in Settings.
- **`User.locale` is what every document renders in, and the UI locale is its source of truth.** PDFs, the receipt email and the digest run outside a request, where the cookie doesn't exist, so they read the column — a column that diverges silently, because `setLocale` writes nothing when signed out (the switcher is on the landing AND login pages) and the client short-circuits when the switcher already shows that language. That shipped: Spanish screens, English receipts, with no way to repair it from the UI. Three writers now keep it honest — `registerAction`, `events.createUser` in `auth.ts` (the adapter creates OAuth users knowing nothing about language), and a reconcile in `app/app/layout.tsx` that mirrors the active locale in `after()` whenever the row disagrees. The reconcile is what heals rows already broken, so **don't "simplify" it away**; the trade-off it buys is deliberate: documents follow the screen, so UI and documents can no longer be in different languages, and on a second device the row follows whatever that device shows.
- Namespaces added for this app's data: `currencies` (currency names), `settings.dateFormats.*` (date-format labels), `datePicker` (picker placeholder/clear).

## Domain conventions

- **Dates**: date-only values (contract dates, paidAt/periodStart, receipt issuedAt) are stored at **UTC midnight**. NEVER read them with local getters (UTC-4 shifts them a day/month back). Use `toDateInputValue()` / `formatDate()` from `format.ts` (UTC-midnight aware) and the same guard for month bucketing (`monthKey` in `shared/lib/rent-period.ts`).
  - **Date DISPLAY format is a user preference** (`User.dateFormat`: `MEDIUM|DMY|MDY|LONG|ISO`, default `MEDIUM`). Core in `src/shared/lib/date-format.ts` (`makeDateFormatter(pref, locale)`, `dateFormatPattern`, `toDateFormat`). Don't hardcode a pattern for UI dates — use the bound formatter: **server components** call `getFormatDate()` (`date-format.server.ts`, reads prefs + active locale); **client components** call `useFormatDate()` from `DateFormatProvider` (mounted once in `app/app/layout.tsx`). `formatDate(value, pattern, { locale })` now takes an optional date-fns locale for month names. PDFs/receipts/statements keep their own document formatting (not the UI preference); statement period labels use `MMMM yyyy`.
  - **Dashboard greeting** (`Buenos días/tardes/noches`) is resolved on the CLIENT (`features/dashboard/components/greeting.tsx` + `shared/lib/greeting.ts`) — the server clock is UTC on Vercel and the app stores NO timezone preference (the browser's clock is a better source — it follows the user when they travel), so a server-rendered greeting is wrong for anyone outside UTC. Bands follow the LatAm convention (05–11 días · 12–18 tardes · 19–04 noches): the madrugada is "buenas noches", never "buenos días". The page passes a server-computed `initialKey` only so hydration matches.
  - **Date inputs**: use `DatePicker` (`ui/date-picker.tsx`, value = `yyyy-MM-dd`; optional INCLUSIVE `minDate`/`maxDate` grey out the days outside them, stop the month navigation there and open an empty field on the bound instead of on today — to exclude the bound itself, pass the neighbouring day, which is how the contract form makes the end date land strictly after the start) and `MonthPicker` (`ui/month-picker.tsx`, value = `yyyy-MM`) — NOT native `<input type="date/month">` (their display format can't be controlled). Both show the value in the user's format/locale and are drop-in for the old inputs. Built on **react-day-picker v10** + `ui/popover.tsx` + `ui/calendar.tsx` (radix popover; the nav keeps `z-20` and the caption `pointer-events-none` so the full arrow stays clickable). **The nav is a SIBLING of the month, not part of the caption** — react-day-picker renders it that way — so it must be taken out of the flow (`absolute inset-x-0` over a `relative` `months`): left as a flex item its absolutely-positioned buttons give it zero width while `months`'s `gap-4` still reserves 16px beside it, which reads as stray padding down the left of every calendar (and above it on mobile). **The `day` cell carries its own `size-9`** — a day outside `startMonth`/`endMonth` still renders its `<td>` but with NO button inside, and since `week` is a flex row a cell sized only by that button collapses to 0 and shifts the rest of the week left (1 May 2026, a Friday, drawn under Monday). Verify a calendar change by rendering it with `renderToStaticMarkup` and reading the first week's cells; layout bugs like this one are invisible to the type checker and to every test. `MonthPicker` takes optional inclusive `min`/`max` (`yyyy-MM`) that disable the months outside them, stop the year arrows at the edge and keep the grid off a fully-disabled year — they compare as plain strings, since zero-padded `yyyy-MM` sorts chronologically.
- **Currency (multi-currency with FX conversion — "Money Lover" model)**: every money row (contract/payment/expense/receipt/deposit settlement) carries its own `currency`, chosen freely per contract (its payments/receipts inherit it). The **primary currency** (`getUserPreferences().currency`, labeled "Moneda principal" in Settings → Formato) is (a) the DEFAULT preselected for new contracts/expenses and (b) the currency the **dashboard & reports convert everything to**.
  - **Live FX rates**: `src/shared/lib/exchange-rates.ts` — `getUsdRates()` fetches `open.er-api.com/v6/latest/USD` (free, no API key, base USD, covers DOP + all LatAm), cached 24h via Next `fetch(..., { next: { revalidate: 86400 } })` (auto-refresh, no cron, no DB). `makeConverter(rates, target)` → a `Converter` you call as `(amount, from) => number` using the cross-rate `amount × rate[target]/rate[from]`; same-currency or missing-rate → 1:1 fallback (never crashes/drops a total). The converter also carries `canConvert(from)` (pure predicate) and `missing` (a Set of currencies it was asked to convert but couldn't) — see the `ratesUnavailable` rule below.
  - Dashboard/report services & the deposit/expense repos `groupBy(['currency'])`, convert each group with the `Converter`, and sum. `dashboard.service` and `report.service` take the primary `currency` and build the converter internally.
  - **≈ approximate marker**: a total shows a leading `≈` **only when that specific total combined a non-primary (converted) currency** — it's per-metric (`revenueApprox`/`expensesApprox` on the summary/`report.approx`) and **per-point in charts** (each series point carries `revenueApprox`/`expensesApprox`; the Recharts tooltip reads `item.payload`). A single-currency total (even if it's the only currency) stays exact, no ≈. **A currency with no rate does NOT earn an ≈** — `reduceGroups` sets `approx` only when `convert.canConvert(currency)`, because an unconverted amount isn't rounded, it's wrong.
  - **Deposits held** breakdown: each item stays in its ORIGINAL currency; only the grand total is converted (≈ if any held deposit is non-primary), and the ≈ is suppressed when `ratesUnavailable`.
  - **`ratesUnavailable` (rates API down)**: `getUsdRates()` returns `{}` on any failure, so every amount falls back to 1:1 — adding RD$ to US$ raw, which can be off ~60×. `DashboardSummary.ratesUnavailable` / `YearlyReport.ratesUnavailable` are `convert.missing.size > 0`, **read at the END of the builder** (the Set fills as conversions run). The dashboard and reports pages render `<RatesUnavailableNotice />` (`shared/components/`, `fx` i18n namespace) instead of a misleading ≈.
  - Currency options: curated `CURRENCY_CODES` in `src/shared/lib/currencies.ts` (kept in sync with `CURRENCY_SYMBOLS` in `format.ts`); human names in the `currencies` i18n namespace; rendered as a `<Select>` (contract form + settings), not a text input.
  - `formatCurrency` renders **USD as `US$`**, DOP → `RD$`, and other known LatAm codes with their prefix; unknown codes fall back to `Intl.NumberFormat`.
- **Contract term dates**: the end date must be strictly AFTER the start, enforced in three places because each one alone leaks. The `endAfterStart` refine covers create and renew; `updateContractSchema` can only check the pair when BOTH arrive (every field there is optional), so `contractService.update` re-checks against the STORED row — a payload carrying only `endDate` would otherwise leave a lease ending before it began. The forms grey the impossible days out and re-run `trigger('endDate')` when the start moves, so the error shows immediately rather than on save.
  - **`endDate` is CLEARABLE and that path was broken**: `update` mapped it with `?? undefined`, which Prisma reads as "leave this column alone", so switching a lease to open-ended reported success and kept the old date (the exact failure the optional-fields rule describes). The service now passes `rest.endDate` through and the form emits `null`, not `undefined`, when the field is cleared.
- **Phones**: use the shared `PhoneInput` (`ui/phone-input.tsx`, react-phone-number-input, default country DO, stores E.164); validate with `isPossiblePhoneNumber`; display with `formatPhone()`.
- **Receipts**: numbers are per-owner sequential, generated inside the payment transaction (`payment.service.ts`). PDF render + upload + tenant email run post-commit (`finalizeReceipt` → `receiptService.generatePdf`, idempotent) — never inside the transaction. The receipts page backfills missing PDFs with `after()`. The PDF template (`src/pdf/documents/receipt-document.tsx` + `receiptStyles`) mirrors the owner's paper format (navy bar, pink date/total, auto-notes incl. next-rent due date, signature over "RECIBIDO POR"). Owner signature: Settings → Profile, either **draw it** (`signature-pad.tsx` — a canvas + pointer-events pad that exports a cropped transparent PNG) or upload a PNG; both go through `updateSignatureAction` → `User.signatureUrl` (storage key `signatures/{ownerId}`). Canvas gotcha: size the backing store to the *displayed* rect (× dpr) lazily on first stroke and map pointer coords as plain CSS px — sizing before the dialog is laid out draws offset.
  - **Deleting a payment frees its receipt number for reuse.** `reserveReceiptNumber` takes the MAX existing number for the owner/year, and the delete is a hard delete, so removing REC-2026-0004 makes the next receipt 0004 again. `@@unique([ownerId, number])` guarantees no duplicate, and the new PDF overwrites the same storage key — but a tenant who already received the deleted receipt now holds a number that belongs to a different row. Fine for re-registering the same payment (the intended use), so the delete dialog names the number it is about to free (`payments.delete.receiptReuse`) rather than blocking: nothing records whether a receipt was actually delivered, and only the owner knows.
  - **Resending**: `receiptService.emailToTenant()` → `sendReceiptAction` → the `SendReceiptButton` row action on `/app/receipts`, for receipts whose delivery was unticked at registration or failed post-commit. Gotcha: `generatePdf` hands back the rendered BYTES only when it actually had to build the file — for a receipt that already has one it returns just the URL — so `emailToTenant` pulls the bytes back from storage (`downloadPdf`) and throws rather than mail a receipt with nothing attached. The button confirms first and names the destination address (real mail to a third party); a tenant with no email on file gets a muted explained icon, not a disabled button nobody can get a tooltip out of.
- **Payments — THE RENT PERIOD MODEL (rewritten 4 sep 2026; read this before touching any date maths).** A period runs from the contract's **start day** to the same day next month, so a lease running 1 May 2026 – 1 May 2027 has exactly twelve periods, 1st to 1st. `rentPeriodStart(date, anchorDay)` builds one at UTC midnight from `contractAnchorDay(startDate)`, never from `paidAt`'s own day: a payment made Aug 4 or Aug 20 on a 15th-anchored lease both settle "15 Aug – 15 Sep". Default concept is built server-side in the owner's language only when the field is blank.
  - **`dueDay` is NOT the period anchor — it is only when the rent must be PAID**, exactly what the UI has always called it ("Día de pago · Día del mes en que vence el alquiler"). `dueDateForPeriod(period, dueDay)` places it inside the period it pays for, rolling into the next month when the due day precedes the anchor (starts the 25th, due the 5th ⇒ the 25 Aug period is due 5 Sep). `period <= due < nextPeriod` is guaranteed and unit-tested across every anchor/due-day pair.
  - **This replaced anchoring periods to `dueDay`, which was wrong** and was reported as a bug: a lease starting 1 May with due day 28 described its periods as "28 Apr – 28 May", offering April on a contract that began in May, and never lining up with the contract's own dates. Three features had each invented their own notion of a period — the payment service used the due day, the dashboard the calendar month of `periodStart`, the reminder scheduler `startOfMonth(now)`. They all go through `rent-period.ts` now. `nextDueDate` was deleted with the old model; use `dueDateForPeriod`.
  - **`periodContaining(date, anchorDay)` is "the period running now"** (what the dashboard and the scheduler need), distinct from `rentPeriodStart`, which returns the period anchored in that date's own month — on 4 Sep with a 15th anchor that one has not started yet. `nextPeriod` re-anchors, so 31 Jan → 28 Feb → 31 Mar rather than degrading to the 28th for the rest of the lease.
  - **Never use date-fns on a period.** `rent-period.ts` imports none, on purpose: `addMonths`, `startOfMonth` and `format` walk dates in LOCAL time, and periods are UTC-midnight values. At UTC-4 `addMonths(1 May, 1)` returns **31 May** (and 1 Mar → 29 Mar, three days off), while `format` prints 1 May as "30 de abril" — which is what the receipt's default concept was doing off-Vercel. Use `rentPeriodEnd`, `monthRangeOf` and `formatDate` (`format.ts`, UTC-midnight aware). This is silently correct on Vercel (UTC) and wrong everywhere else, which is the worst way for it to fail.
  - **Pure rules live in `shared/lib/` and are unit-tested**, because each is shared by two features that must agree: `rent-period.ts` (`rentPeriodStart`, `rentPeriodEnd`, `periodContaining`, `nextPeriod`, `contractAnchorDay`, `dueDateForPeriod`, `monthKey`, `monthRangeOf`, `periodToMonthValue`, `monthValueToDate`, `shiftMonthValue`, `firstUncoveredMonth`, `isPeriodWithinTerm`, `periodMonthBounds`), `rent-settlement.ts` (`settlesRentPeriod`, `rentBalanceAfter`, `isPeriodCovered`), `receipt-number.ts` (per-owner sequence) and `deposit-split.ts` (retained/returned). Services keep the DB work and call these — do NOT re-implement the arithmetic inline.
  - **Prepayment = one payment per period, with the period chosen in the form.** There is deliberately NO credit/balance concept: `rentBalanceAfter` documents that overpaying leaves 0, not credit. So paying two months at once is TWO payments, each with its own `periodStart` and its own receipt — the tenant gets a document per month, which is what the PDF template is built for. The alternative shapes were considered and rejected: a `monthsCovered` column forces every aggregation to expand one row into N buckets and breaks on 1.5 months; a credit ledger is a whole new concept for a fixed monthly amount.
    - The form sends only a MONTH (`MonthPicker`, `yyyy-MM`); the service anchors it with `rentPeriodStart(input.periodStart ?? input.paidAt, contract.dueDay)`, so **the client never needs the due day** and any day-of-month the client sends is normalised. Always run an incoming `periodStart` through `rentPeriodStart` — using it raw stores an unanchored date and the default concept then prints the wrong range.
    - `paymentService.coveredPeriods()` feeds the form's default (first unpaid month) and its block. It MUST decide coverage with `isPeriodCovered` — the same rule the dashboard uses for "upcoming payments" — or the form suggests a month the dashboard still shows as due.
    - **A settled month REFUSES a second payment** (3 sep 2026; it used to warn and let it through). Without a credit concept that payment records money and advances nothing, so the form paints the message in `text-destructive` and disables submit, and `paymentService.register` re-checks with `periodTally` + `isPeriodCovered` and throws a translated `ConflictError` (`payments.errors.periodAlreadyPaid`) — the page can be stale, so the service is the guarantee, not the form. **This does NOT block a second PARTIAL**: coverage needs `paid >= rent` or `settlesPeriod`, so a month still short of the rent takes more money as before.
    - **A period must belong to the contract's TERM** (3 sep 2026): paying April on a contract running 15 Jul 2026 – 15 Jul 2027 used to go straight through. `isPeriodWithinTerm` decides it and `periodMonthBounds` turns a term into the `yyyy-MM` `min`/`max` the `MonthPicker` greys out; `register` re-checks and throws `payments.errors.periodOutsideContract`. The bounds are resolved SERVER-side (the list page, `payments/new/page.tsx`) so the client gets two strings instead of dates it would have to re-anchor.
      - Membership is **overlap, not containment**. With periods anchored to the start day the lower edge is exact (the starting month's period begins ON `startDate`; the one before it ends there and falls out), so this only matters at the far end, where a term can stop mid-period — a lease ending 15 Jun on a 1st-to-1st cycle still has to bill the 1 Jun period covering fifteen real days.
      - **The field shows the MONTH and the hint shows the exact range, on every contract.** Both forms did this conditionally for a while (range in the field when the anchor wasn't the 1st) to stop "Abril 2026" appearing on a lease starting in May — a symptom of the old due-day anchor, gone now that the month shown always belongs to the contract. What was left was two contracts rendering the same field differently, and a closed field showing a date range above a picker that selects months. Keep it unconditional.
      - It compares by **DAY, not by instant**. Contract dates are supposed to be UTC midnight, but rows exist at `T04:00:00Z` (a local midnight that was never normalised — check with a query before assuming otherwise). Comparing raw timestamps gave every one of those contracts an extra month, because the period starting the morning the term ended still counted as overlapping.
    - `update` runs both guards with `excludePaymentId`, but **only when the month actually CHANGES** (`previousMonth`, derived from the row's own `periodStart`/`paidAt`). Editing in place must keep working on the rows registered before the guards existed — a duplicated month, a period outside the term — or the fix would strand exactly what it exists to prevent.
    - The edit dialog exposes the field but NOT the default/block: you are editing a payment whose period is covered by itself. A move onto a covered month comes back from the service as a toast — the dialog has no `coveredPeriods` of its own (it would cost one query per row of the list).
  - **`periodTally` is what keeps the receipt and the dashboard agreeing.** `rentBalanceAfter` takes `alreadyPaid` (what the period's OTHER payments put on it) because the dashboard sums a month while the receipt used to read one payment: a 500 + 700 split on a 1200 rent printed "owes 700" on the second receipt and re-fired the partial notification, with the dashboard already calling the month covered. Matched by MONTH, not by exact `periodStart`, so a changed `dueDay` or a legacy row with no `periodStart` still lands in the right bucket — same bucketing as `coveredPeriods`.
  - **A lost receipt-number race is retried, not surfaced.** `reserveReceiptNumber` is a read-then-write, so two truly concurrent registrations propose the same number and `@@unique([ownerId, number])` rejects one with P2002 — not an `AppError`, so it used to reach the owner as the generic failure. `withReceiptNumberRetry` re-runs the whole transaction (which rolled back entirely, leaving no half-written payment) up to `RECEIPT_NUMBER_RETRIES`.
  - **Partial vs full**: normally `amount < monthlyRent` ⇒ a rent balance remains and the contract keeps showing in "upcoming payments". `Payment.settlesPeriod` (Boolean, additive, default false; DEPOSIT ignores it) overrides that — the period is treated as fully paid (no `balanceAfter`, no partial notification, drops out of upcoming) even for a lower **agreed** amount (e.g. a discount). The form/edit-dialog toggle "Cubre el período completo" shows only when it's a rent payment below the rent; the dashboard treats a month as covered when `paid >= rent` OR any of its payments is `settlesPeriod`.
- **Auth**: credentials login REQUIRES a verified email (`EmailNotVerifiedError`, code `email_not_verified`); OAuth (Google/GitHub) skips verification by design (providers verify) and uses `allowDangerousEmailAccountLinking` deliberately. OAuth logins land on `/app?welcome=1` so `WelcomeToast` can fire (credentials toast client-side in the form).
- **Statements cover a rent PERIOD, not a calendar month** (4 sep 2026). The owner picks a month and `statementService.generate` resolves it on the contract's own cycle (`rentPeriodStart` + the anchor), so a 15th-to-15th lease reads "15 Jul – 15 Aug". Its payments are the ones that SETTLE that period (matched by month, like `periodTally`), not the ones whose `paidAt` fell inside it — that older rule double-counted an advance payment in the month it was PAID and left the month it COVERED showing a full balance due. Duplicates are detected by month so statements written under the old rule (sitting on the 1st) still block a second one. Every date the PDF prints goes through `formatDate`, since these are UTC-midnight values.
- **Reminders are in-app AND email — as ONE digest per owner per day.** The scheduler writes `Notification` rows (the bell at `/app/notifications`), then `sendReminderDigests()` (`notification-digest.ts`) mails each owner a single email listing everything still unsent. One email per reminder would burst past a free sending tier on the 1st of the month, when due days cluster. **Statements are still download-only** — never describe them as emailed.
  - **`Notification.emailedAt` is the retry ledger, and it is why the two phases are separate.** The scheduler de-dupes off the notification ROW, so a failed send would otherwise be skipped forever. `sendReminderDigestEmails()` returns the `ref`s (owner ids) the provider ACCEPTED — not a count — and only those rows get stamped; a failed chunk is simply picked up tomorrow. `MAX_AGE_DAYS = 3` stops a week-long outage from dumping a fifty-line backlog.
  - `User.notifyByEmail` (default true) is delivery, not a fourth reminder: the three `notify*` toggles decide which reminders EXIST, this one decides whether they also leave the app. Settings → Recordatorios, last row.
  - The job runs outside a request, so each owner's locale is passed explicitly to `getTranslations({ locale, namespace: 'notifications' })` — the digest reuses the SAME `notifications.*` keys the in-app panel renders, so item copy never forks. Resolve one translator per locale, not per row.
  - `reminderDigestEmail()` **escapes its items** (`escapeHtml` in `templates.ts`): unlike every other template, it interpolates the owner's own property/tenant names. Unit-tested in `emails/__tests__/templates.test.ts`.
  - Email still leaves the app in only these places, all via `emails/send.ts`: welcome, verify-email, reset-password and the daily digest (to the OWNER), and the receipt (to the TENANT).
- **Reminders**: the daily cron (`vercel.json` → `/api/cron/notifications` → `notification-scheduler.ts`) reads **per-owner** prefs from `User`: `notifyContractExpiring` + `contractExpiringLeadDays` (default 30), `notifyPaymentUpcoming` + `paymentUpcomingLeadDays` (default 3), `notifyPaymentLate`. Each reminder type is muted by its toggle and uses its lead days as both the window and the de-dupe window. Configured in Settings → Recordatorios.
  - **The cron schedule is UTC, always** (`0 12 * * *`). Vercel does not do local time, so it fires at **08:00 in the Dominican Republic** (GMT-4 year-round, no DST) — not at noon. On the **Hobby plan the precision is per-hour (±59 min)**, so the real invocation lands anywhere in the 08:00–08:59 window; do not look for it at an exact minute. A genuine run is identifiable in the Runtime Logs by the `vercel-cron/1.0` user agent and the `x-vercel-cron-schedule` header — anything else hitting that path is a manual call.
- **Settings structure**: "Formato" (currency + date format) and "Recordatorios" are **one form** — `preferences-form.tsx` / `updatePreferencesAction` / `updatePreferencesSchema` — with a single save button; password is its own form. The old **"Idioma" and "Zona horaria" fields were removed**: UI language is set ONLY by the **topbar language switcher** (`setLocale` in `i18n/actions.ts` → cookie `NEXT_LOCALE` AND mirrors `User.locale`); there is **no timezone preference at all** — the `User.timezone` column was dropped (21 ago 2026) after confirming nothing ever read it: domain dates are date-only at UTC midnight (offsetting them would move them a day) and the only real-clock need, the greeting, resolves on the client.
- **User preference columns** (all additive, defaults): `currency`, `locale`, `dateFormat`, `signatureUrl`, `notifyContractExpiring`, `contractExpiringLeadDays`, `notifyPaymentUpcoming`, `paymentUpcomingLeadDays`, `notifyPaymentLate`. All already applied to prod.

A plain `1fr` (= `minmax(auto,1fr)`) can't shrink below its min-content width, so a wide table blew the whole document out horizontally between `lg` and ~`xl`. Keep both the `minmax(0,…)` track and the `min-w-0`; the `Table` primitive's `overflow-auto` wrapper then scrolls on its own only when needed.
- **Brand mark**: a rounded-square indigo tile (`#48509e`, `rx` 20.88 on a 95.98/128 box) holding three overlapping figures in white at 100 % / 50 % / 20 % opacity, drawn in that order so the fainter ones sit on top. Source artwork is the designer's `favicon-1.svg` / `logopropio_1.svg`; both are reproduced verbatim, only reformatted (class-based `<style>` → inline `fill`/`fill-opacity`).
  - `shared/components/brand/logo.tsx` is the single on-screen lockup (landing header + footer, auth layout, app sidebar, mobile nav, 404). One inline SVG; `showWordmark` just swaps the viewBox between the full lockup (`0 0 307.15 95.98`) and the tile (`0 0 95.98 95.98`), so tile↔wordmark spacing stays the designer's. Sized by height (`h-8 w-auto`), never `size-*`.

The wordmark can't be: the brand indigo *as a text colour* on the dark background (`224 20% 8%`) is only ~2.6:1. So light gets the exact `#48509e` of the designer's artwork, dark gets near-white — matching the tile's own glyphs, which is the standard dark-mode wordmark treatment. Two dead ends already tried: `currentColor` (turns it near-black in light, NOT the artwork) and a merely lightened indigo in dark (legible at 5.5:1 but visibly dull and washed out next to the sidebar).
  - The whole accent system was realigned to it (25 ago 2026): `--primary`/`--ring` are `234 37% 45%` (= `#48509e`) in light and `234 45% 65%` in dark, and `pdf/styles.ts` `colors.primary` + `emails/templates.ts` `brand.color` are the literal `#48509e`. **Dark mode must keep the lightened value** — the literal brand indigo is 2.6:1 on the dark background, so links, focus rings and outline buttons would vanish. The receipt PDF's own navy/pink palette (`receiptColors`) is NOT part of this: it mirrors the owner's paper format and stays untouched.
- **Three app icons on purpose**: `src/app/icon.svg` (crisp, what modern browsers pick via `sizes="any"`), `src/app/favicon.ico` (16/32/48 PNG-in-ICO) and `src/app/apple-icon.png` (180×180, flattened onto `#48509e` because iOS ignores transparency and rounds the corners itself). Next emits a `<link>` for each. The `.ico` is not redundant: plenty of clients request `/favicon.ico` DIRECTLY without parsing the HTML — link previews in WhatsApp/Slack/Telegram, feed readers, crawlers — and that path 404'd while only the SVG existed. Regenerate both raster icons from `icon.svg` if the brand mark changes: `sharp` (already a transitive dep) rasterizes at high `density`, then pack the three PNGs into an ICO container by hand — ImageMagick's ICO writer emits BMP frames (~15 KB vs ~2.3 KB).
  - Known limit: at **16 px the three figures merge into one blob** — inherent to the artwork's density, not the conversion. It's fine from 32 px up. Live with it or ship a simplified single-figure 16 px frame.
- `PageHeader` actions wrap on mobile (`flex-wrap`, `sm:flex-nowrap`); for a busy header (e.g. contract detail) make the primary action `w-full sm:w-auto` and group secondaries. Dialogs (`ui/dialog.tsx`) use `w-[calc(100%-2rem)]` so they don't touch mobile edges.

## Public site (landing + legal)

Everything unauthenticated lives in `src/features/marketing/components` and is composed by `src/app/page.tsx` (landing) and `src/app/(legal)/{terms,privacy}` (which share `(legal)/layout.tsx`). `SiteHeader` + `SiteFooter` are shared by all three. All copy is in the `landing` and `legal` i18n namespaces — no hardcoded marketing strings.

- **Ignore the dev-console warning** “Please ensure that the container has a non-static position…” (shows in the terminal via Next 16's browser-log forwarding). It is framer-motion's generic advisory for any `useScroll({ target })` whose container is the default `document.documentElement` — static on every website. Dev-only (`NODE_ENV` guard), measurements verified correct in-browser. Do NOT “fix” it with `html { position: relative }`; that changes the containing block of every unanchored absolute element globally.
- **Animation is `framer-motion`** (already a dependency, previously unused). The shared wrappers are in `motion-primitives.tsx` — `Reveal` and `Marquee` — and **both honour `prefers-reduced-motion`** (`useReducedMotion`, plus `motion-reduce:animate-none` on the CSS-driven marquee). Don't hand-roll a new scroll animation; extend those.
  - **`Reveal` is the only scroll-in primitive, on purpose.** It owns its own `whileInView`, so it animates correctly however it got mounted. A parent/child `staggerChildren` pair does NOT: with `once: true` the parent stops observing once it fires, so any child that remounts afterwards inherits the parent's `hidden` variant and is never told to become visible. That shipped once and broke the before/after panel — switching language calls `router.refresh()`, and the rows were keyed by their own translated text, so every row remounted and stayed at `opacity: 0`. Stagger a group with per-item `delay={index * 0.06}`, and **never key a list by a translated string** (use the message key).
  - `motion.div` redefines `onAnimationStart`/`onDrag*`, so a component wrapping it must take `HTMLMotionProps<'div'>` — `React.HTMLAttributes<HTMLDivElement>` is NOT assignable and TS 7 rejects it.
  - The hero's 3D stage composes TWO transforms by nesting: scroll drives `rotateX`/`scale` on the outer layer (which carries `transformStyle: preserve-3d`), the pointer drives `rotateY` on the inner one. Putting both on one element makes the later `style` win and the tilt disappears.
- **Section anchors are plain `<a>`, NEVER `next/link`.** Next's segment-cache navigation builds the new canonical URL by string concatenation — `route.canonicalUrl + url.hash` (`client/components/segment-cache/navigation.js`). Once a route entry has been seeded from a URL that already carried a hash (the visitor reloaded on `/#features`), every further hash navigation APPENDS instead of replacing: `/#features#features#features`, forever. It hits the relative and absolute forms identically, so `/#features` is not a workaround — only staying off the router is. The browser's native fragment navigation is correct, honours `scroll-mt-*`, and a same-page anchor needs no prefetch or RSC round-trip anyway. Real route links (`/login`, `/terms`…) keep `next/link`.
  - **The same cache defect bites links to `/` that carry NO hash.** There `url.hash` is empty but `route.canonicalUrl` still holds the stale one, so the brand logo would send a visitor who reloaded on `/#reviews` straight back to that section instead of the top of home. Both logo links — `site-header.tsx` and `(auth)/layout.tsx` — are plain `<a href="/">` with a scoped `@next/next/no-html-link-for-pages` disable: the full navigation IS the fix, not a regression.
- **Smooth anchor scrolling is scoped, not global**: `globals.css` sets `scroll-behavior: smooth` via `html:has([data-smooth-scroll])`, and only the landing root (`page.tsx`) and the legal layout carry that attribute. Putting it on `html` unconditionally would animate the router's scroll-to-top on EVERY app navigation. Gated on `prefers-reduced-motion: no-preference` like the rest of the marketing motion. The landing sections use `scroll-mt-6 sm:scroll-mt-0` — NOT the header-height offset you'd expect — because each section carries 80/112px of internal top padding (`py-20 sm:py-28`): the offset compensates for it so the HEADING lands ~40–48px below the sticky header instead of the section's empty edge landing there with ~128px of dead air. The top edge sliding under the translucent header is fine (it's padding). The legal pages keep `scroll-mt-24`: their sections have no internal padding, the heading IS the top edge.
  - **Mobile-menu anchors CANNOT use native fragment navigation** while smooth scroll is on. Browser-verified with headless Chrome: the tap's synchronous React re-render (closing the menu) plus the panel's first exit-animation frame kill the smooth scroll before it starts — hash changes, `scrollY` stays 0, no JS errors; instant scroll never hit this because it completes synchronously during navigation. The panel's links therefore `preventDefault`, stash the hash, close with a DURATION-0 exit (the `closed` variant is dynamic via `custom` — anchor taps close instantly so the scroll starts ~100ms after the tap, the X button keeps the animated fold), and `AnimatePresence.onExitComplete` runs `history.pushState` + `target.scrollIntoView()` — no `behavior` on purpose, so it follows the CSS scroll-behavior (smooth where allowed, instant under reduced motion) and honours `scroll-margin-top`. The panel itself is an absolute overlay (`top-full`), never in-flow: in flow its collapse shifted the whole page mid-scroll.
  - **The landing root carries `overflow-x-clip`** (never `-hidden`, which would create a scroll container and un-stick the header): Reveal's ±24–32px pre-entrance side offsets and the showcase glows extend the document's scroll area — measured 422px on a 390px viewport — and put a horizontal scrollbar on mobile.
- **The hero and the legal pages are pulled up with `-mt-16` and padded back out.** The header is transparent until you scroll, so without the pull-up the page opens with a flat strip above the gradient.
- Landing keyframes (`marquee`, `marquee-reverse`, `float`, `aurora-drift`, `pulse-ring`) live in `globals.css` — `@keyframes` plus an `--animate-*` token in `@theme` (there is no `tailwind.config.ts` since the v4 migration). The marquee track holds its children **twice** and translates `-50%`, so the seam is invisible; `--marquee-duration` sets the speed per instance.
- **There is deliberately NO testimonials section.** The landing first shipped six invented quotes; when asked to write fictional reviews that “look genuine” (28 ago 2026), that was declined — fabricated endorsements presented as real customers are deceptive advertising — and the slot became `use-cases.tsx`: six landlord-persona cards (`landing.useCases`, anchor `#use-cases`, nav/footer keys `navUseCases`/`useCases`), second person, no names, no cities, no star ratings, static grid (the old marquee visibly repeated its three cards per row). When real, attributable reviews exist, resurrect `reviews.tsx` + the `landing.reviews` catalogue block from git history — and only then. Do not reintroduce invented quotes or ratings.
- The legal documents are **data, not markup**: `legal.terms.sections` / `legal.privacy.sections` are arrays of `{title, body[], bullets[]}` rendered by `legal-document.tsx`, which narrows `t.raw()` instead of trusting it and derives both the section `id`s and the table-of-contents anchors from the same `slugify`. Editing a clause never means touching a component, and EN/ES stay structurally identical.
- **`legal`, `pdf` and `emails` are stripped from the client message payload** in `app/layout.tsx` (`SERVER_ONLY_NAMESPACES`). `NextIntlClientProvider` otherwise serialises the WHOLE catalogue into every page's HTML, and those three are the long-form prose ones, read only via `getTranslations({ locale, namespace })` on the server. Add a namespace to that list when it is server-only; remove it the moment a client component needs it.
- `ThemeToggle` (`shared/components/theme-toggle.tsx`) picks its icon with CSS (`dark:hidden` / `dark:block`), not React state — `next-themes` only resolves the theme after hydration, and the `mounted` flag pattern trips `react-hooks/set-state-in-effect`.

## Gotchas

- **`src/proxy.ts`** (Next 16 renamed the `middleware` convention to `proxy`) uses the edge-safe `auth.config.ts`; Node-only providers live in `auth.ts`. Two traps, both of which fail SILENTLY because `app/layout.tsx` also guards with `redirect('/login')`:
  - It must export the function as `default` (or a named `proxy`). `export const { auth: proxy } = NextAuth(...)` is a destructured binding and Next's static analysis rejects it: "must export a function".
  - The matcher needs a REAL escaped dot: `.*\\..*` in the source string. Written `.*\..*` the string collapses to `.*..*`, which matches every path of 1+ characters, so the proxy silently stops running everywhere except `/`. Verify with `curl -o /dev/null -w '%{http_code}' localhost:3000/app` — it must be **307**, not 200.
  - `proxy` always runs on the **Node.js** runtime; the edge runtime is not supported there.
- Env is validated at boot in `src/shared/config/env.ts`; server env import from client code throws.
- **Windows EPERM on `prisma generate`**: the dev server (or a stray node/VS Code TS server that keeps respawning) locks the query-engine DLL. Kill node processes right before `prisma generate`/`db:push`/`yarn build`, then relaunch `yarn dev`. (`--skip-generate` no longer exists on `db push` in Prisma 7.)
- Never run two dev servers at once — they share `.next` and corrupt each other (500s). **`.next` corruption is common after EPERM/killed processes**: `next build` fails with `MODULE_NOT_FOUND` / "Failed to collect page data", or dev throws `Cannot find module './vendor-chunks/...'` → `rm -rf .next` and rebuild (fixes it).
- **Testing server modules**: `vitest.config.ts` aliases `server-only` to `src/test/server-only-stub.ts`, and sets fake `DATABASE_URL`/`AUTH_SECRET` under `test.env` — `shared/config/env.ts` validates the WHOLE server env at import time, so any module that reaches it (the email templates pull `clientEnv`) fails to load without them. They are deliberately fake: pointing them at the real `.env` would aim unit tests at the dev database. Without it any module with `import 'server-only'` throws on import under Vitest and can't be unit-tested. Don't drop the `server-only` import from source to make a test pass.
- **DROPPING a column is the reverse of adding one**: additive columns go to prod BEFORE the code. A drop must go AFTER the code that stops reading it is deployed — the live build still `select`s the old column and every query using it throws the moment it disappears.
- **Applying schema to prod** (Prisma 7 changed every flag here): prod DB URLs live in the gitignored `.env.production`. **Careful — Next auto-loads `.env.[mode]`**, so a local `next start` (NODE_ENV=production) loads this file and connects to the PRODUCTION database; `yarn dev` only reads `.env` (dev). Verify with `NODE_ENV=production node -e "require('@next/env').loadEnvConfig(process.cwd(), false); console.log(process.env.DATABASE_URL)"` before running anything in production mode locally. `prisma.config.ts` reads `DIRECT_URL` from the process env, so export it first:
  ```bash
  set -a && eval "$(grep -E '^(DATABASE_URL|DIRECT_URL)=' .env.production)" && set +a
  npx prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script   # REVIEW first
  npx prisma db push --accept-data-loss
  npx prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --exit-code  # 0 = in sync
  ```
  Gone in 7: `db push --skip-generate`, `db execute --url/--schema`, `migrate diff --from-url/--to-schema-datamodel`. For a **destructive** change (dropping a column) prefer `prisma db execute --file drop.sql` over `db push --accept-data-loss`, which would apply every drift it finds. Prod project host is `aws-*-us-east-2`.
- GitHub OAuth apps allow only ONE callback URL (prod vs localhost); Google allows several.
- **The GitHub provider needs an explicit `issuer`** (`auth.ts`). This project's GitHub credential is a GitHub **App** (client id `Ov23li…`), not a classic OAuth App, and GitHub Apps append an `iss` parameter to the OAuth callback. Auth.js validates `iss` against `provider.issuer`, which its GitHub provider leaves unset — it then falls back to the placeholder `https://authjs.dev` and EVERY callback dies with `unexpected "iss" (issuer) response parameter value`, surfaced to the user as the opaque `Configuration` error. Hence `issuer: 'https://github.com/login/oauth'`. Classic OAuth Apps send no `iss`, and Google never did either, which is why only GitHub was broken — from day one, never a single `github` row in `accounts`.
- **Do NOT add columns to `Account` for extra provider token fields.** `@auth/core`'s `defaultAccount` whitelists exactly `access_token`, `id_token`, `refresh_token`, `expires_at`, `scope`, `token_type`, `session_state` before the adapter runs, so anything else (`expires_in`, `refresh_token_expires_in`…) is dropped and can never reach Prisma.
- **Prisma 7 enums must be imported from `@/generated/prisma/enums`, never `/client`.** The generated client is TypeScript source inside `src/`, so a `'use client'` component importing an enum from `/client` drags `node:module` into the browser bundle and Turbopack fails with "does not support external modules". `enums.ts` has zero imports. Only server-only files import from `/client` (that is where the `Prisma` namespace types live).
- **Why two TypeScript versions**: `typescript-eslint` (latest, 8.67) declares `typescript >=4.8.4 <6.1.0` and TS 7 hard-errors with "typescript-eslint does not support TS 7.0". So `typescript` resolves to **6.0.3** (what ESLint, Next and the IDE consume via `require('typescript')`), and TS 7.0.2 is installed under the npm alias `typescript7` purely to run the type check. Both check the same code with the same semantics; TS 7 is just ~13× faster (0.3s vs 4s). Note `node_modules/.bin/tsc` points at the TS 7 binary because the alias package also ships a `tsc` bin — that is why both typecheck scripts call their compiler by explicit path. Collapse this back to a single `typescript` once typescript-eslint supports 7.x.
- **Tailwind is on 4.x (migrated 4 sep 2026 with `@tailwindcss/upgrade`).** There is NO `tailwind.config.ts` any more — the theme lives in `src/app/globals.css` as `@theme`, the container as `@utility container`, and dark mode as `@custom-variant dark (&:is(.dark *))` (the generated selector is byte-identical to what v3 emitted, so dark mode behaves exactly as before). `autoprefixer` is gone (v4 includes it) and PostCSS loads only `@tailwindcss/postcss`.
  - Three things the codemod does NOT do, all done by hand here: `tailwindcss-animate` → **`tw-animate-css`** (imported at the top of `globals.css`; it supplies `animate-in`/`animate-out` and the fade/zoom modifiers every dialog and popover uses), **`tailwind-merge` 2.x → 3.x** (the 2.x line does not know v4 class names and `cn()` depends on it — pinned by `shared/lib/__tests__/utils.test.ts`, which fails loudly on a downgrade), and splitting the font variable (below).
  - **`next/font` must NOT use `--font-sans`.** That name is Tailwind's own theme token, so `@theme { --font-sans: var(--font-sans), … }` is a circular reference that silently drops the fallback stack. The font is `--font-inter` and the token composes it.
  - **The v4 default border colour (`currentcolor`) is irrelevant here** and the upgrade's `gray-200` compatibility shim was deleted: this project has always set the colour from its own token in `@layer base`, now covering the same selectors v3's preflight did (`*`, `::after`, `::before`, `::backdrop`, `::file-selector-button`). The other changed default, ring width 3px → 1px, cost nothing either — every ring in the codebase already specifies a width.
  - CSS grew 58.5 KB → 89.8 KB raw but only **9.8 → 12.2 KB brotli**, which is what actually ships. Not worth optimising.
- **ESLint is pinned to 9.x, not 10**: `eslint-plugin-react@7.37.5` (latest, and a dependency of `eslint-config-next`) peers at `<=9` and crashes under ESLint 10 with `contextOrFilename.getFilename is not a function`.
- **Line endings**: the repo stores LF (`.gitattributes` has `* text=auto`) and Prettier enforces `endOfLine: "lf"`, so `git config core.autocrlf` must be **`input`** on Windows.
